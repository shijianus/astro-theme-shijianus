# EpoCanvas 發布與事件處理手冊

<div class="article-aside">
  <p><span class="badge badge-primary">OPS-001</span> <span class="badge badge-success">發布與事件</span> <span class="badge badge-warning">需明確授權</span></p>
  <p>本手冊供專案維護者在文件、程式、配置或生產服務發生變更時使用。它要求每個結論都能回溯至命令、提交、部署、網址與時間，不把歷史報告或介面截圖當成當前證據。</p>
</div>

> [!WARNING]
> 本手冊不授權自動推送、Cloudflare Pages 部署、D1 migration、真實支付或外部服務管理。執行生產操作前，必須取得本次任務的明確授權，並確認目標專案與回滾方案。沒有執行的步驟要標記為「未執行」。

## 1. 證據等級與責任

發布紀錄使用以下分類：

| 標記 | 可支持的說法 | 最低證據 |
| :--- | :--- | :--- |
| `SOURCE-VERIFIED` | 源碼、設定或路由存在某項行為 | 檔案路徑、函式/配置與提交 |
| `TEST-VERIFIED` | 指定環境曾通過建置或自動化測試 | 命令、退出碼、斷言、時間與提交 |
| `LIVE-VERIFIED` | 指定生產網址曾觀測到某項行為 | URL、部署識別、時間、請求/瀏覽器結果 |
| `KNOWN-GAP` | 已知兩側行為或文件與實作不一致 | 差異、影響範圍與重現方式 |
| `BLOCKED` | 因授權、憑證、平台或外部決策無法執行 | 阻塞原因、責任邊界與替代檢查 |

「建置成功」只支持 `TEST-VERIFIED` 的建置結論；「已提交」不支持線上可見；「頁面回應 200」也不代表評論、登入、支付或通知的完整鏈路健康。

## 2. 發布前準備

### 2.1 確認範圍與工作區

1. 讀取根目錄 `AGENTS.md`、`GUIDES.md` 與適用的子目錄規範；
2. 記錄當前分支、完整 `git rev-parse HEAD` 與 `git status --short`；
3. 確認工作區既有的使用者修改，不覆蓋、不重置、不把無關檔案加入本次提交；
4. 列出本次明確修改的文件、程式、測試、配置與路由；
5. 搜尋新增或修改內容是否包含密碼、API 金鑰、Cookie、會話令牌、私有 URL、內部 IP 或完整個資。

若工作區本身已有未提交變更，發布前必須能區分本次提交與其他變更。無法安全隔離時，停止發布並先取得維護者決策。

### 2.2 建置與測試

依變更風險選擇檢查：

- 文件/路由變更：`git diff --check`、Markdown/front matter 檢查、Astro 靜態建置；
- 內容集合或版本變更：確認 schema、版本 manifest 與建置期同步指令沒有產生未審核差異；
- UI/互動變更：執行對應的 Playwright/Puppeteer 測試，涵蓋桌面、行動與鍵盤/模態框狀態；
- API/資料庫變更：執行單元或整合測試，檢查 JSON 錯誤格式、權限、限流、migration 與失敗分支；
- 支付/帳號/通知變更：使用明確標記的沙盒資料，確認不會把測試訊息、卡號或真實個資送入生產通知。

每個命令都要記錄執行時間、環境、退出碼與重要輸出。只看到本地成功不能直接寫成線上已驗證。

## 3. 提交與發布追溯

每個獨立子任務應形成可審閱的單一提交：

1. 只 stage 本次範圍內的檔案；
2. 使用描述變更目的的提交訊息；
3. 執行 `git rev-parse --short HEAD` 與 `git show --stat --oneline HEAD`；
4. 在交付報告中列出 Commit Hash、測試結果與未執行項目；
5. 若建置指令修改版本清單、快照或產生檔案，檢查差異後再決定是否納入提交。

提交 Hash 是源碼追溯證據，不是部署證據。不可手寫、猜測或沿用歷史任務的 Hash；也不可為了讓工作區乾淨而對使用者修改執行破壞性 reset/checkout。

## 4. 推送與 Cloudflare Pages 邊界

生產同步與部署是兩個需要分別記錄的動作：

1. 先確認遠端名稱、目標分支、目標 Cloudflare Pages 專案、環境變數與是否影響真實業務；
2. 只有在取得明確授權後，才執行 `git push` 或其他遠端同步；
3. `shijianus-blog` 專案只能使用本專案的建置產物與目標設定，不可把其他專案的產物跨專案部署；
4. 部署前使用對應的靜態建置流程，並確認機密只從環境變數/平台 secrets 注入，不寫入 Markdown、JavaScript 或產物；
5. 部署後記錄 Pages deployment ID、Commit SHA、目標域名、時間與命令結果；
6. 如果沒有授權、憑證或部署必要資訊，狀態應為 `BLOCKED` 或「未執行」，不能以本地成功代替發布。

倉庫中的 `npm run cf:deploy` 只是可用命令，不是自動批准。生產部署若涉及資料庫 migration、密鑰輪換、支付、帳號或通知，還要逐項記錄相容性與回滾限制。

## 5. 線上驗證

只有部署已獲授權且產物已在目標環境生效後，才進行生產驗證。最低紀錄應包括：

- 目標網址，例如 `https://blog.epocanvas.com/`；
- Pages deployment ID、Commit SHA、驗證日期、時間與時區；
- 受影響頁面與 API 的 HTTP 狀態、內容類型與關鍵回應；
- 需要互動時，使用無頭瀏覽器檢查載入、點擊、模態框、表單、錯誤提示、響應式佈局與控制台致命錯誤；
- 受影響的資料流是否使用沙盒或真實資料，以及是否有外部副作用；
- 失敗時的原始輸出、截圖/錄影位置與是否已止損。

文件路由可以只驗證頁面標題、正文、連結與無 404；評論、帳號、支付或通知則必須驗證其相應 API 和權限邊界。不能用一個首頁 200 回應代替全部功能驗收。

## 6. 事件分級與立即處理

### 6.1 文件或建置事件

若文件無法解析、路由 404、front matter 錯誤、靜態建置失敗或產物包含不應公開的內容：

1. 停止推送與部署；
2. 保存錯誤命令、提交、檔案路徑與環境；
3. 若尚未部署，修正後重新建置；
4. 若已部署，依授權的上一個健康產物或最小修正方案回退；
5. 更新文件狀態與交付報告。

### 6.2 API、資料與身份事件

若出現未授權讀取/修改、評論資料遺失、會話失效、公開個資或 migration 異常：

1. 先限制受影響路由或停止後續 migration；
2. 撤銷/輪換疑似外洩的令牌與 secrets，不把秘密貼到報告；
3. 保存請求時間、部署識別、錯誤回應與受影響資料類型；
4. 依[安全問題通報規範](/community/security-disclosure/)與[隱私與資料使用說明](/community/privacy-and-data/)處理通知與資料請求；
5. 未確認資料一致性前，不宣稱「已恢復」或「資料完整」。

### 6.3 支付與通知事件

若 Stripe、讚賞記錄、退款、Telegram 通知或支付狀態出現異常：

- 不要重放未知狀態的支付請求，不要在評論或郵件中索取卡號/安全碼；
- 分開保存支付供應商回應、本站記錄、通知結果與時間線；
- 先確定交易是否已完成、重複扣款是否可能發生，再決定重試或退款路徑；
- 把通知未送達與支付未完成分開處理，不能以 Telegram 訊息作為唯一交易證據；
- 依[贊賞、退款與第三方支付說明](/community/support-and-refunds/)向使用者說明可用處理方式。

## 7. 回滾與恢復

回滾前應確認目標是「程式/文件產物」、「資料庫 schema」、「環境變數」還是「第三方交易狀態」；它們不一定可以用同一個動作恢復。

1. 選定已知健康的提交/部署識別，並確認它沒有包含仍需保留的資料庫 migration 或安全修正；
2. 先保存現況與事故證據，再執行經授權的回退；
3. 不使用破壞性 Git reset/checkout 來抹掉未確認的使用者修改；
4. 回退後重新做受影響路由與 API 的最小線上驗證；
5. 若資料已寫入或支付已發生，另外執行資料修復、退款或人工核對，不把頁面回退誤當成資料回復；
6. 在事故結束後補上根因、時間線、影響、修正、未解決風險與後續測試。

## 8. 交付報告模板

```text
任務類型：文件 / 程式 / API / 配置 / 運維
檢查基線：分支、完整 HEAD、工作區既有修改
實際修改文件：列出檔案與路由
證據等級：SOURCE-VERIFIED / TEST-VERIFIED / LIVE-VERIFIED / KNOWN-GAP / BLOCKED
已執行命令：命令、時間、退出碼與關鍵結果
測試結果：建置、單元、E2E、API 或無障礙檢查
線上驗收：網址、部署識別、時間；未執行則寫明原因
已知問題：影響範圍與暫時處理方式
未執行項目：推送、部署、migration、真實支付等
Commit Hash：完整或短 SHA
部署版本：未部署 / deployment ID
回滾方式：目標提交、部署或資料修復步驟
```
