# EpoCanvas 專案路線圖

<div class="article-aside">
  <p><span class="badge badge-primary">PROJECT-001</span> <span class="badge badge-success">專案管理</span> <span class="badge badge-warning">公開規劃</span></p>
  <p>本頁由專案維護者整理，用來說明哪些能力已經落地、哪些差異已被記錄，以及接下來值得優先處理的工作。它不是個人願望清單，也不是對任何日期、性能或服務水準的保證。</p>

> [!IMPORTANT]
> 路線圖只表示目前的優先順序與驗收方向。只有同時具備原始碼、測試或生產觀測證據的項目，才可以標記為已落地；沒有明確提交與驗收紀錄的項目，仍屬於 `PROPOSED`，不應被理解為已經提供的功能。

## 1. 狀態標記與閱讀方式

| 標記 | 本頁的意思 | 需要什麼證據 |
| :--- | :--- | :--- |
| `DONE` | 目前版本已具備，且已完成與範圍相稱的驗證 | 來源檔案、提交、建置/測試或線上驗收紀錄 |
| `KNOWN-GAP` | 已確認存在的行為差異、資料邊界或文件缺口 | 可重現的兩側差異、影響範圍與暫時使用方式 |
| `PROPOSED` | 尚未正式落地的設計或工程工作 | 目標、風險、驗收條件與遷移前置條件 |
| `BLOCKED` | 需要外部憑證、平台能力、法律判斷或其他尚未取得的條件 | 阻塞原因、依賴對象與可繼續工作的替代方案 |

路線圖不使用「快要完成」「即將上線」等沒有可驗證含義的描述。若工作內容改變，應更新本頁的狀態、影響範圍與對應提交，而不是只修改標題或進度顏色。

## 2. 目前基線

以下是本頁更新時可以從專案結構與公開路由核對的基線。它描述能力邊界，不代表所有外部服務持續健康。

| 工作面向 | 狀態 | 目前可核對的內容 | 主要入口或證據 |
| :--- | :---: | :--- | :--- |
| 社群政策 | `DONE` | 社群公約、評論審核、隱私、授權、使用條款、身份徽章與檢舉申訴已分頁整理 | `/community/` 與 `docs/community/` |
| 工程標準 | `DONE` | 活躍等級、內容密度、版本協議與系統狀態分開說明，並標示證據等級 | `/standards/`、`/version/`、`/status/` |
| 正體中文官方基線 | `DONE` | 本路線圖與目前官方政策/標準文件優先以正體中文維護 | 各文件 front matter 的 `lang: zh-Hant` |
| 內容統計 | `KNOWN-GAP` | 頁面側與快照指令碼在公開文章過濾、多語言歸組及時間視窗上仍有已記錄差異 | 《工程標準總綱》中的 `KNOWN-GAP` 清單 |
| 評論契約 | `KNOWN-GAP` | 前端一般評論上限與服務端驗證上限尚未完全一致；訪客與登入者限流也必須以服務端回應為準 | 《評論與審核規範》 |
| 生產可觀測性 | `PROPOSED` | 尚未建立把靜態站點、D1、支付與通知拆開的公開健康語義 | 《系統狀態與服務邊界》 |

「`DONE`」只適用於上表所描述的狹窄範圍。例如，標準頁已經可以在線上渲染，不代表所有評論、支付或第三方通知都已經具有相同的線上驗證等級。

## 3. 已落地的工作面

### 3.1 社群政策與權利邊界 `DONE`

官方政策已從單一、分散的介面文案整理為可獨立引用的文件群：

1. 《社群公約》定義尊重交流、禁止行為、站務處置與申訴入口；
2. 《評論與審核規範》說明一般評論、回覆、Boost、Reaction、限流與公開欄位；
3. 《隱私與資料使用說明》區分評論、帳號、讚賞與安全審計資料的來源與公開邊界；
4. 《內容授權與版權說明》區分程式碼、文章、留言、商標與第三方素材；
5. 《使用條款》、《身份等級與徽章說明》及《檢舉與申訴說明》補足使用責任、顯示層等級與處理入口。

這些文件是互相連結的政策集合，不把一次成功的請求、頁面徽章或付款記錄當成安全權限，也不把讚賞與社群等級綁在一起。

### 3.2 工程指標與證據分層 `DONE`

工程標準文件已將以下概念分開：

- 近 30 天公開文章的釋出活躍度；
- 公開文章的估算篇幅與平均值；
- Git 提交、內容版本與部署識別；
- 靜態建置、邊緣函式、D1、支付與通知的服務邊界；
- `SOURCE-VERIFIED`、`TEST-VERIFIED`、`LIVE-VERIFIED`、`KNOWN-GAP` 與 `PROPOSED` 的證據分類。

這種分層的目的，是讓「程式碼存在」與「生產環境曾經觀測到」保持可區分。後續新增指標時，也必須沿用相同的證據語義。

## 4. 已知差異與處理順序

### 4.1 指標資料鏈路差異 `KNOWN-GAP`

頁面側的公開文章集合、建置期指標快照與請求期動態校準並非完全共用一套純函式。這可能造成以下可觀察差異：

- 多語言文章的代表版本在不同資料鏈路中未必使用相同的歸組鍵；
- `access` 受限文章的過濾邏輯需要與公開文章集合持續對齊；
- 核心活躍指標與發文明細使用的 30 天下界演算法不同；
- 熱力圖、統計快照與頁面顯示的生成時間可能不同。

在統一前，讀者應以對應頁面的規則、資料生成時間與服務端回應為準。任何把這些差異描述成「所有介面永遠一致」的文案都不符合目前實作。

### 4.2 評論與身份差異 `KNOWN-GAP`

評論前端、評論 API、客戶端 LV/TL 引擎與服務端身份映射分屬不同模組。短期內採取以下保守原則：

1. 字數、限流、Reaction 權限與管理操作以服務端驗證結果為準；
2. 公開頁面的 LV、TL 或徽章只作為顯示資訊，不自動授予 API 權限；
3. 訪客會話失去所有權證明後，不應繼續宣稱可以編輯或刪除原留言；
4. 在統一資料模型前，政策文件必須保留差異說明，不把其中一套客戶端表格升格為永久合約。

### 4.3 生產狀態缺口 `PROPOSED`

目前可以核對路由是否能回應，以及某次建置或瀏覽器測試是否成功；但這不足以提供持續性服務水準。後續若要公開狀態，至少需要：

- 明確區分靜態頁面、評論資料、支付建立、支付確認與通知送達；
- 為每一類狀態記錄採樣時間、部署 SHA、請求條件與原始結果；
- 將降級回應標記為 `degraded` 或等價狀態，避免把資料庫讀取失敗誤顯示為「目前沒有評論」；
- 定義維護窗口、告警門檻、重試與資料恢復責任，再考慮是否需要公開承諾。

## 5. 後續工作優先序

以下是建議順序，不是截止日期，也不表示所有項目都已獲得實作承諾。

### P0：資料與安全邊界

1. 統一評論前端與服務端的字數契約，並為一般評論、回覆與 Boost 分別保留測試案例；
2. 為評論資料庫失敗與空集合 fallback 增加可觀測的降級訊號；
3. 建立資料類型、用途、公開欄位、管理欄位與刪除例外的維護矩陣；
4. 重新檢查支付、通知與退款文案，只保留可以由實際通道與紀錄支持的說法。

### P1：一致性與追溯

1. 提取頁面側與快照指令碼共用的 canonical group key 與公開文章過濾函式；
2. 讓指標 API 回傳快照生成時間、動態校準時間與版本識別，避免只顯示一個模糊的 `servedAt`；
3. 讓內容版本、Git SHA、建置輸出與 Pages deployment ID 可以由同一份發布紀錄互相追溯；
4. 將文件中的 `KNOWN-GAP` 轉換為可重跑的回歸測試，而不是只依賴人工閱讀。

### P2：閱讀體驗與語言擴充

1. 在正體中文官方文件的規則與鏈接穩定後，再規劃英文及其他語言版本；
2. 為政策與工程文件補充鍵盤操作、焦點順序、表格閱讀與錯誤提示的可及性檢查；
3. 為文章、政策頁與互動元件分別建立內容審校清單，避免把普通文章的語氣直接套用到社群規範。

## 6. 工作項目的最低驗收條件

任何項目在本頁由 `PROPOSED` 轉為 `DONE` 前，至少應具備：

- 一個清楚的範圍與不包含項目；
- 對應的原始碼、配置或文件位置；
- 與風險相稱的建置、測試或瀏覽器驗收結果；
- 可追溯的 Git Commit SHA；
- 若涉及生產行為，還要記錄目標專案、部署識別、網址、時間與原始結果；
- 若涉及個人資料、付款或第三方服務，補充失敗、刪除、退款與申訴邊界。

若只完成介面草稿、設定檔新增或本地單次點擊，狀態最多只能是 `PROPOSED` 或 `TEST-VERIFIED`，不能直接寫成「已上線」或「已穩定運作」。

## 7. 不在本頁承諾的內容

本路線圖不承諾以下事項：

- 全球節點數、固定延遲、固定冷啟動時間或任何未建立採樣方法的 SLA；
- 第三方支付、登入、通知、DNS 或雲端平台的持續可用性；
- 尚未完成的多語言翻譯、語義分詞、自然語言防刷或自動化審核；
- 任何以讚賞金額、徽章或社群等級換取的審核豁免、管理權限或付費內容；
- 沒有經過實際權利核對的文章、圖片、程式碼或第三方資料授權。

## 8. 更新規則

每次更新路線圖時，應同步檢查：

1. 項目狀態是否仍有來源證據；
2. `KNOWN-GAP` 是否已有新的重現方式或修正提交；
3. `PROPOSED` 是否仍值得保留，或已因範圍、風險與外部依賴而取消；
4. 涉及公開資料、支付、登入與社群處置的變更，是否已同步更新相應政策文件；
5. 頁面更新日期、內容版本與發布紀錄是否一致。
