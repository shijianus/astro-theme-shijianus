# EpoCanvas 內容撰寫規範

<div class="article-aside">
  <p><span class="badge badge-primary">EES-007</span> <span class="badge badge-success">內容工程</span> <span class="badge badge-warning">以實際建置為準</span></p>
  <p>本規範同時服務於官方政策、工程標準、專案管理文件與普通文章。它規定內容如何進入 Astro、如何被讀者理解，以及如何避免把未驗證資訊或敏感資料寫進公開產物。</p>
</div>

> [!IMPORTANT]
> 目前專案的文章與官方文件入口以 Markdown/MDX 為主。檔案能被 Markdown 解析器接受，不等於內容中的 API、權限、支付或安全說法已經正確；內容審閱與工程驗證仍然是必要步驟。

## 1. 文件位置與內容類型

不同目錄承擔不同責任：

| 內容 | 位置 | 寫作要求 |
| :--- | :--- | :--- |
| 社群政策 | `docs/community/` | 以共同規則、權利邊界、限制與聯絡入口為主；不能用個人語氣取代政策定義 |
| 工程標準 | `docs/standards/` | 必須說明資料來源、演算法、證據等級、已知差異與不承擔的承諾 |
| 專案管理 | `docs/roadmap.md` | 只列可追溯的已落地、已知差異、建議工作與阻塞條件 |
| 運維文件 | `docs/operations/` | 以可執行步驟、權限邊界、失敗處理與驗收證據為主 |
| 普通文章 | `src/content/posts/` | 可以有個人觀點、實驗與敘事，但不自動成為官方契約 |

若一段內容需要被所有讀者當作規則、權限或安全邊界引用，應寫入適當的官方文件，並從文章連結過去；不要只在普通文章中留下唯一版本。

## 2. Markdown/MDX 與 front matter

目前建置透過 Astro 的 Markdown/MDX 管線處理內容，文章集合的欄位以 `src/content.config.ts` 的 schema 為準。常用欄位包括：

```yaml
title: "文件或文章標題"
description: "供頁面摘要與分享使用的簡短說明"
pubDate: 2026-10-20
updatedDate: 2026-10-20
author: "EpoCanvas 工程團隊"
tags: ["文件"]
category: "工程規範"
toc: true
draft: false
lang: "zh-Hant"
```

官方文件可以依需要補充 `version`、`i18nKey`、`math`、`mermaid`、`mindmap` 等欄位；實際可用欄位與型別以 schema、路由與建置結果為準。不要自行新增前端不會讀取的欄位，並不要把密碼、令牌、私有 URL、個人資料或第三方服務秘密寫在 front matter 註解或範例裡。

`draft: true` 的內容不得被當作已發布規則。日期應使用可解析的 ISO 日期；若文件已有 `version`，內容改變時要依[文件生命週期規範](/standards/document-lifecycle/)判斷是否提升版本。

## 3. 結構、標題與連結

一篇可維護的官方文件通常應依以下順序組織：

1. 一句話說明目的與適用範圍；
2. 警告、免責或證據等級；
3. 目前規則、資料流或操作步驟；
4. 已知限制、失敗模式與不包含項目；
5. 核驗方式、聯絡入口與更新日期。

標題應從 `#` 開始並按層級遞進，不用標題製造純視覺大小。表格要有清楚欄名，長表格應在正文解釋如何閱讀。站內連結使用穩定的絕對路徑，例如 `/community/privacy-and-data/`；改名或移動文件時，同步檢查總覽、頁尾、元件與其他文件的引用。

不要用截圖取代可搜尋的規則、用顏色取代狀態文字，或把一段沒有來源的數字寫成「官方統計」。若使用流程圖、數學式或自訂 HTML，仍需提供文字說明與失效時的可讀內容。

## 4. 程式碼、命令與範例

程式碼範例應符合以下原則：

- 標示語言，保持縮排與必要的上下文；
- 只使用可公開的示意值，例如 `YOUR_TOKEN`、`example.com` 或明確的假資料；
- 交代命令的執行目錄、前置條件、預期輸出與可能的破壞性影響；
- 涉及 migration、部署、刪除、支付或管理員操作時，標記環境與授權要求；
- 若範例來自第三方，保留來源、版本與授權，不能把第三方程式碼自動標成專案原創；
- 寫清楚「可執行範例」與「概念示意」的差別。

公開文件不得包含真實的 API 金鑰、密碼、Cookie、會話令牌、私有資料庫 URI、內部 IP、未公開 webhook 或可直接重放的支付識別資訊。即使內容只是註解、測試樣本或已失效憑證，也應視為需要清理的敏感資料。

## 5. 文章中的資料、權限與安全說法

涉及下列主題時，正文必須補充證據來源與限制：

| 主題 | 最低要求 |
| :--- | :--- |
| API | 路由、方法、輸入/輸出、身份要求、錯誤狀態與是否為目前實作 |
| 帳號/權限 | 分開描述瀏覽器顯示與服務端鑑權，不以徽章或 LV/TL 推導權限 |
| 個人資料 | 來源、用途、公開欄位、管理存取、保留/刪除限制與聯絡方式 |
| 支付/退款 | 第三方責任、付款核驗、失敗、退款與不可承諾的部分 |
| 效能/SLA | 採樣方法、環境、時間窗與原始結果；沒有監控就標為待驗證 |
| 安全 | 私下通報入口、測試授權、止損方式與不公開的資料邊界 |

如果程式碼、測試和文件的行為不一致，應明確寫成 `KNOWN-GAP`，並提供保守的使用方式。不要以「已支援」「安全」「即時」「永久」「100%」等字眼掩蓋沒有測試或生產證據的範圍。

## 6. 可及性與閱讀品質

正文、表格與互動元件的內容應照顧鍵盤、讀屏、縮放、深色模式與行動裝置閱讀：

- 有意義的圖片提供替代文字，裝飾圖片不塞入冗長描述；
- 重要狀態同時使用文字、語義元素或可讀標籤，不只依靠顏色和 Emoji；
- 連結文字描述目的，程式碼與表格保留必要的上下文；
- 長文使用小節、列表、摘要與明確的錯誤/警告區塊；
- 不用過度動畫、閃爍或自動播放替代閱讀內容；
- 編輯完成後在合理的桌面與行動視窗檢查溢出、焦點與連結。

完整的回報與已知限制見[無障礙與可及性說明](/community/accessibility/)。

## 7. 寫作驗收清單

### 7.1 官方文件

- [ ] 文件放在正確的 `docs/` 目錄，且有對應 Astro 路由或入口。
- [ ] front matter、標題、描述、日期、語言與版本欄位可解析。
- [ ] 現況、已知差異、建議方向與外部阻塞已分開。
- [ ] 站內連結、路由、檔案路徑與程式碼名稱已核對。
- [ ] 沒有秘密、未遮蔽個資、未授權素材或虛構性能/可用性承諾。
- [ ] 涉及程式碼的說法有相應測試或明確標記證據等級。

### 7.2 普通文章

- [ ] 文章觀點與官方政策分開，必要時連回政策頁。
- [ ] front matter 符合文章集合 schema，`draft` 與日期正確。
- [ ] 程式碼命令能在說明的條件下重現，示例秘密已使用假值。
- [ ] 圖片、引用、第三方程式碼與資料有來源或授權說明。
- [ ] 讀者可以從標題、摘要、目錄與小節理解文章結構。
