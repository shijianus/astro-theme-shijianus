## 1. 標準的目標與適用範圍

EpoCanvas Engineering Standards（簡稱 EES）是本站對內容指標、資料鏈路及其對外解釋方式的專案級工程約定。

它主要回答三個核心問題：

1. 站點近期是否在持續穩定地釋出或維護公開技術內容？
2. 已公開文章的平均物理篇幅處於什麼區間，呈現怎樣的體量分佈？
3. 所有對外展示的統計數值與等級，能否根據明確的輸入、演算法與時間條件被完整獨立復算？

EES 拒絕把多維度的複雜工程質量壓縮為一個單一的分數。發文數量、文章篇幅、頁面效能、服務可用性和認證安全分別屬於完全不同的工程領域，必須由不同型別的真實證據進行獨立支撐。

例如：
- 近 30 天內沒有釋出新文章，只代表釋出視窗計數為零，絕不代表全站評論系統、邊緣函式或部署鏈路發生故障；
- 全站平均篇幅較長，只代表文本規模達到特定字元區間，絕不自動證明每篇文章都具備高質量、原創性、邏輯嚴密性或易讀性；
- 服務端響應正常，只能證明 API 路由處理邏輯可執行，不能反向證明歷史快照中的統計規則已經消除所有邊界差異。

### 1.1 文件體系結構

EES 規範體系由一個總綱與四個專項子規範構成，各文件分工如下：

| 規範編號 | 規範領域 | 核心職責與系統邊界 | 權威資料來源 |
| :--- | :--- | :--- | :--- |
| **EES-001** | 工程標準總綱 | 頂層指標體系組織、資料鏈路流向、核驗邊界與一致性原則 | `src/config/standards.ts` |
| **EES-002** | 活躍等級模型 | 近 30 天滑動視窗釋出頻次計算、五級離散閾值與時間邊界 | 部落格文章集合與時序釋出流 |
| **EES-003** | 內容密度模型 | 正文字數精算演算法、全站平均篇幅、四級閾值與閱讀耗時 | 文章純文本內容長度特徵 |
| **EES-004** | 版本協議規範 | 語義化版本控制、不可變 Git SHA 追溯、架構分層與授權邊界 | Git 倉庫提交元資訊與環境變數 |
| **EES-005** | 系統狀態與服務邊界 | 靜態建置、邊緣函式、資料儲存、支付/通知邊界、失敗模式與證據等級 | `docs/standards/status.md`、`functions/` 與部署設定 |

當前配置檔案標識與基線版本：

| 配置專案 | 原始碼對映 / 當前取值 | 說明與約束 |
| --- | --- | --- |
| 標準標識 | `EES-2026.4` | 當前執行的標準代號 |
| 配置版本 | `2.6.0` | 配置檔案中宣告的版本標識 |

### 1.2 規範用語約定

本文件遵循嚴格的技術規範表達約定：

- **必須 (MUST)**：表示在生成資料、輸出指標或釋出內容前必須嚴格滿足的硬性約束；
- **應當 (SHOULD)**：表示工程上的推薦最佳實踐，偏離此做法時必須給出明確的技術解釋與上下文；
- **可以 (MAY)**：表示可選功能或未來擴充套件能力；
- **當前實現 (SOURCE-VERIFIED)**：表示已從當前提交版本的原始碼中確認的實際行為；
- **已知差異 (KNOWN-GAP)**：表示已經確認存在但尚未在程式碼中徹底統合的雙軌邏輯差異；
- **建議方向 (PROPOSED)**：表示處於設計或遷移規劃中、尚未實際落地的改進方案。

## 2. 證據基線與技術宣告分類協議

為杜絕技術文件中常見的過度宣稱與虛假修飾，EES 體系建立嚴格的宣告分類協議。所有面向讀者的技術結論必須能夠歸入以下可驗證類別之一：

| 標識程式碼 | 分類名稱 | 定義與含義 | 可接受的證據支撐 |
| --- | --- | --- | --- |
| `SOURCE-VERIFIED` | 原始碼已核驗 | 行為已從倉庫現有原始碼中得到確認 | 具體檔案路徑、函式名、分支條件程式碼與 Git 提交 Hash |
| `TEST-VERIFIED` | 測試已核驗 | 邏輯已通過實際執行自動化測試驗證 | 明確的執行命令、程序退出碼 0、具體斷言項與測試日誌 |
| `LIVE-VERIFIED` | 線上已核驗 | 功能已在生產線上環境完成端到端驗證 | 生產域名、實測時刻、網路請求抓包或真實瀏覽器渲染證據 |
| `KNOWN-GAP` | 已知差異項 | 雙側或歷史遺留實現之間存在已記錄的分歧 | 兩側程式碼實現差異對比、影響範圍與可復現用例 |
| `PROPOSED` | 建議演進項 | 經過架構設計的擬定方案，尚未正式合併 | 詳細介面設計說明、預期收益、風險評估與遷移前置條件 |
| `BLOCKED` | 外部阻塞項 | 因外部環境、憑證或許可權不足而無法完成 | 具體阻塞原因、依賴的外部團隊或鑑權邊界說明 |

禁止將僅在原始碼中存在的邏輯描述為已在線上環境驗證（嚴禁將 `SOURCE-VERIFIED` 混淆為 `LIVE-VERIFIED`）。

## 4. 核心指標字典

EES 規範所涉及的核心指標欄位、資料型別、計量單位與工程含義定義如下：

| 指標名稱 | 資料模型欄位 | 單位 | 核心工程定義與計算口徑 |
| --- | --- | --- | --- |
| 公開文章總量 | `stats.posts` | 篇 | 當前資料來源中經過去重與過濾後納入統計的代表性公開文章數量 |
| 全站估算總字數 | `stats.totalWords` | 字 | 納入統計的全部公開文章通過字數估算演算法得到的分值之和 |
| 全站平均篇幅 | `stats.avgWordsPerPost` | 字/篇 | 全站總字數除以公開文章總量後四捨五入（`Math.round`）所得的算術平均值 |
| 預計總閱讀時間 | `stats.readingMinutes` | 分鐘 | 逐篇文章按估算字數除以閱讀速率並向上/取整後的閱讀分鐘數直接累加值 |
| 近 30 天發文量 | `stats.recentPostCount30d` | 篇 | 釋出日期（`pubDate`）落入計算時刻往前滑動 30 天視窗內的文章總數 |
| 活躍等級 | `stats.activeLevel` | 等級 | 由近 30 天發文量匹配 `activityLevels` 階梯表所得的評級物件 |
| 內容密度等級 | `stats.densityLevel` | 等級 | 由全站平均篇幅匹配 `contentDensityLevels` 階梯表所得的評級物件 |
| 累計執行天數 | `stats.uptimeDays` | 天 | 從固定起始錨點 `2024-01-01T00:00:00Z` 到計算時刻之間經過的完整日曆日數 |
| 52 周動態熱力圖 | `activity` | 格子陣列 | 包含 364 個日曆格子的矩陣，記錄首次釋出與有效更新事件的日期分佈 |
| 快照生成時刻 | `generatedAt` | ISO-8601 | 構建指令碼掃描文章正文生成 JSON 資料資產的具體時間戳 |
| 介面處理時刻 | `servedAt` | ISO-8601 | 邊緣函式接收到 HTTP 請求並完成部分欄位重算的時間戳 |

### 4.1 “累計執行天數”的技術邊界澄清

在當前實現中，`stats.uptimeDays` 由以下程式碼計算：

```ts
const START_DATE = '2024-01-01T00:00:00Z';
const uptimeDays = Math.floor(
  (now.getTime() - new Date(START_DATE).getTime()) / (1000 * 60 * 60 * 24)
);
```

這是一個以固定日期為起點的**站點存在時間計數器（Site Age Indicator）**，絕不是基於高可用叢集探針、心跳監測或 SLA 統計的“零故障無中斷執行時長”。

因此，在對外展示與工程文件中：
- 不能將執行天數解釋為站點期間從未發生過任何宕機、崩潰或網路中斷；
- 不能將該數值替代真實的 HTTP 存活探針或雲廠商 SLA 監控報表；
- 介面展示建議採用“建站天數”或“累計執行天數”，避免產生誤導。

## 5. 資料實際如何流動：三條並行鏈路

本站指標並不存在“每次客戶端請求都即時查詢 Cloudflare D1 資料庫並全文掃描 Markdown”的邏輯。全站資料通過三條職責明確的鏈路流轉：

```text
【鏈路一：靜態頁面構建鏈路 (SSG Build Pipeline)】
src/content/posts/*.{md,mdx}
  │
  ▼ getCollection('posts')
Astro 內容集合框架
  │
  ▼ getPublicPosts()
排除草稿、排除 access 限制、依據 i18nKey 進行多語言歸組
  │
  ▼ calculateSiteMetrics()
記憶體計算全站總字數、平均字數、近期發文與等級階梯
  │
  ▼ standards/ 頁面靜態渲染
注入頁面初始 HTML（構建時刻的確定性靜態映象）

【鏈路二：構建期快照同步鏈路 (Snapshot Pipeline)】
src/content/posts/*.{md,mdx}
  │
  ▼ scripts/sync-console-metrics.mjs
提取 Frontmatter、正則預清理正文、計算字數與 52 周熱力圖
  │
  ▼ 生成靜態資產
public/data/console-metrics.json（隨靜態資產部署至目標 Pages/CDN 資產層）

【鏈路三：邊緣 API 請求期動態校準鏈路 (Edge Runtime Pipeline)】
客戶端發起 GET /api/console/data
  │
  ▼ Cloudflare Pages Functions
優先從 ASSETS 快取讀取 console-metrics.json 快照
  │
  ▼ 基於當前請求時刻 (now) 重新校準：
  - 累計執行天數 uptimeDays
  - 近 30 天滑動視窗發文數 recentPostCount30d
  - 動態重評 activeLevel 等級與進度條
  - 基於當前日期重新投影 52 周（364 天）熱力圖格子
  │
  ▼ 輸出 HTTP JSON 響應
附帶響應頭 Cache-Control: public, max-age=60, s-maxage=300
```

> [!NOTE]
> “在邊緣函式中執行”描述的是程式碼執行的物理網路節點，不代表“每一次網路請求都會在邊緣節點上重新將幾百篇 Markdown 正文重算一遍”。
> 當前架構的標準技術定性是：**構建期靜態快照驅動，疊加邊緣請求期時間相關欄位動態校準**。

### 6.1 活躍等級對照速查

| 等級標識 | 狀態程式碼 | 徽章顯示 | 近 30 天發文量 | 官方命名 | 創作節奏參考描述 |
| --- | --- | --- | ---: | --- | --- |
| Lv.0 | Status 0 | Lv.0 Idle | 0 篇 | 維護休眠 | 視窗內無新文章，處於常規歸檔或底層休整期 |
| Lv.1 | Status 1 | Lv.1 Low | 1–2 篇 | 週期推送 | 保持每月 1 至 2 篇的基礎技術分享節奏 |
| Lv.2 | Status 2 | Lv.2 Standard | 3–4 篇 | 穩定維護 | 保持雙週更或每週一篇的穩定知識沉澱節奏 |
| Lv.3 | Status 3 | Lv.3 High | 5–8 篇 | 高頻迭代 | 保持高密度周更或多專題並行推進 |
| Lv.4 | Status 4 | Lv.4 Ultra | 至少 9 篇 | 極客狂熱 | 保持極高頻技術輸出與系列專欄集中交付 |

“維護休眠”是針對釋出時間視窗的狀態標記，絕不等於站點已廢棄或維護團隊停止工作。

### 6.2 內容密度等級對照速查

| 等級標識 | 狀態程式碼 | 徽章顯示 | 四捨五入後平均篇幅 | 官方命名 | 篇幅結構技術特徵 |
| --- | --- | --- | ---: | --- | --- |
| Lv.1 | Level 1 (Low) | Lv.1 Low | 0–800 字 | 微動態速記 | 簡明備忘、單點故障修復記錄、短小快速片段 |
| Lv.2 | Level 2 (Standard) | Lv.2 Standard | 801–1500 字 | 標準技術部落格 | 完整敘事的單點專題、標準架構元件解析 |
| Lv.3 | Level 3 (High) | Lv.3 High | 1501–3000 字 | 詳實系統專欄 | 包含多模組聯動、配置演練與程式碼實現的深度文章 |
| Lv.4 | Level 4 (Ultra) | Lv.4 Ultra | 至少 3001 字 | 硬核深度長文 | 體系化全景長文、全鏈路原始碼剖析或重構復盤 |

所有等級命名均屬於本站內部的篇幅結構分類，不構成外部機構的技術認證。

## 7. 統計准入與多語言去重準則

在頁面側計算與公共資料流中，文章是否能參與統計遵循嚴格的過濾流水線：

```text
全部文章集合 (All Posts)
  │
  ├── 1. 過濾 draft === true 的草稿 ────────────► 排除草稿
  │
  ├── 2. 過濾包含 access 屬性的加密/受限文章 ───► 排除受限內容
  │
  └── 3. 多語言版本歸組與去重 (Canonical Grouping)
        │
        ├── 提取分組鍵：優先使用 frontmatter.i18nKey
        │   未配置時回退為：移除已識別語言字尾後的 slug 標識
        │
        └── 同一組別存在多個版本時：
            優先選擇無語言字尾的根版本作為唯一的代表性文章；
            無根版本時，選擇按字母序排列的第一個可用版本。
```

### 7.1 去重機制不是語義防刷模型

當前的去重與防刷邏輯依賴於顯式的 Frontmatter 後設資料與檔名規範。以下行為無法通過當前演算法自動識別：

- 正文高度相似但使用完全不同檔名與不同 `i18nKey` 的文章；
- 將一個完整技術主題人為拆解為十篇幾百字的碎片文章以刷取發文篇數；
- 故意篡改 `pubDate` 為近期日期；
- 將純外鏈引用包裝為長文。

因此，當前系統提供的是**多語言釋出副本與草稿的工程級歸一化**，不能聲稱具備自然語言語義分析級的全自動防刷能力。

### 7.2 已識別的程式碼與架構差異詳錄 (Identified Consistency Gaps)

在對當前倉庫原始碼的完整審計中，確認存在以下雙軌實現差異。在未完成程式碼級統合前，公開文件應如實解釋其技術邊界：

| 差異編號 | 差異簡述 | 影響範圍與表現 | 推薦統一方向 (PROPOSED) |
| --- | --- | --- | --- |
| GAP-01 | 頁面側與快照指令碼的 access 過濾不一致 | 頁面側完全排除 access 文章；快照指令碼未排除，受限文章的標題和日期可能進入公共快照 | 快照指令碼引入與 `getPublicPosts()` 嚴格一致的過濾邏輯 |
| GAP-02 | 多語言分組鍵實現差異 | 頁面側優先支援顯式 `i18nKey`；快照指令碼主要依據檔名規則，存在多語言文章在快照中未歸組的風險 | 提取通用的 `getCanonicalGroupKey()` 共享純函式 |
| GAP-03 | 時間視窗下界計算存在 720h 與零點差異 | 核心指標按前推 30 天當日零點計算；活躍文章明細按嚴格 `30 * 24h` 計算，導致明細行數與指標偶發不一致 | 統一以自然日零點或嚴格毫秒數為唯一判定標準 |
| GAP-04 | 快照資料丟失具體時分秒精度 | 快照中的釋出日期被截斷為 `YYYY-MM-DD` 字串，同一日內的先後順序與時間戳精度丟失 | 快照保留完整的 ISO-8601 時間戳字串 |
| GAP-05 | 站點起始日期多處硬編碼並存 | `src/config/standards.ts` 定義了起始日期，但部分模組仍存在獨立的區域性硬編碼常量 | 全量引用配置檔案中的統一常量匯出 |
| GAP-06 | 等級升級閾值硬編碼於計算函式中 | 進度條百分比與下一等級提示直接硬編碼了數字，修改配置表無法完全自動聯動 | 重構進度計算器，直接消費配置陣列中的區間範圍 |

## 8. 熱力圖的構造原理與解釋限制

全站 52 周動態熱力圖由 364 個日曆格組成，具有固定的排列與著色規則：

```text
52 列 × 7 行 矩陣佈局
行：星期日 (Row 0) 至 星期六 (Row 6)
列：從 52 周前對應的週日至當前周
```

### 8.1 事件提取與色階對映

熱力圖記錄兩類有明確後設資料支撐的內容事件：

1. **首次釋出事件**：基於文章的 `pubDate` 記錄；
2. **有效修訂事件**：當文章存在 `updatedDate` 且其年月日與 `pubDate` 不相同時，作為獨立修訂事件記錄。

單日事件數量到顯示色階的對映關係：

| 當日事件數 $E$ | 對應色階 | 介面視覺表現 |
| ---: | ---: | --- |
| $E = 0$ | 0 階 | 基礎底色（灰色/低透明度） |
| $E = 1$ | 1 階 | 淺度主題色 |
| $2 \le E \le 3$ | 2 階 | 中度主題色 |
| $4 \le E \le 6$ | 3 階 | 深度主題色 |
| $E \ge 7$ | 4 階 | 高飽和高亮主題色 |

### 8.2 關鍵解釋邊界

- **修訂不增加近期發文量**：更新舊文章可以在熱力圖中點亮特定日期的格子，但絕不會增加 `recentPostCount30d`；
- **歷史修訂覆蓋性**：文章模型僅保留單一最新的 `updatedDate`，若一篇文章修改過十次，也只能體現最初發布日與最後更新日兩個點，無法還原完整的版本控制歷史；
- **未來佔位格**：當前周尚未到來的剩餘天數屬於佔位格子，不顯示任何活動。

## 9. API 閱讀與資料新鮮度核驗準則

在通過 HTTP 請求讀取 `/api/console/data` 時，讀者與開發者應遵循嚴格的資料新鮮度驗證流程：

```text
1. 校驗 HTTP 狀態碼為 200，Content-Type 為 application/json；
2. 確認 JSON 頂層 ok 欄位為 true；
3. 檢查 generatedAt 時間戳（明確靜態資料快照的構建時刻）；
4. 檢查 servedAt 時間戳（明確當前邊緣節點的響應時刻）；
5. 明確哪些欄位是請求期重算的（uptimeDays, recentPostCount30d, activeLevel, activity）；
6. 明確哪些欄位是快照固化的（totalPosts, totalWords, avgWordsPerPost, densityLevel）。
```

### 9.1 快取策略與失效機制

當前 API 聲明瞭邊緣網路快取：

```http
Cache-Control: public, max-age=60, s-maxage=300
```

這意味著：
- 瀏覽器本地可在 60 秒內複用快取；
- 共享快取可能依 `s-maxage=300` 在最多 300 秒內複用回應；實際命中、失效與重新驗證仍需在目標環境觀測；
- 即使釋出了新的文章並完成了部署，在共享快取視窗（最長 5 分鐘）完全失效之前，仍可能獲取到上一週期的回應體；
- 遇到網路異常或返回非 JSON 響應時，前端介面應當明確展示“資料暫時不可用”，絕不能將異常靜默回退為“0 篇文章”或“Lv.0”，避免向讀者傳遞虛假的歸零資訊。

## 11. 資料契約與介面序列化規範

邊緣 API 介面（`GET /api/console/data`）與靜態快照（`console-metrics.json`）遵循嚴格的資料模式契約與欄位不變性約束。各消費端（前端中控臺、指標儀表盤、規範頁面）必須基於以下權威 Schema 進行型別對映：

```ts
export interface ConsoleMetricsPayload {
  ok: boolean;
  generatedAt: string; // ISO-8601 快照生成時刻
  servedAt?: string;    // ISO-8601 邊緣請求處理時刻
  stats: {
    posts: number;              // 公開有效文章數 (>= 0)
    totalWords: number;         // 全站估算總字數 (>= 0)
    avgWordsPerPost: number;    // 取整後的平均字數
    readingMinutes: number;     // 逐篇累加總閱讀耗時 (分鐘)
    recentPostCount30d: number; // 滑動視窗發文量 (>= 0)
    uptimeDays: number;         // 站點累計執行日數
    activeLevel: ActivityTier;  // 活躍等級完整物件
    densityLevel: DensityTier;  // 內容密度等級完整物件
  };
  standardsConfig: {
    specId: string;             // 如 "EES-2026.4"
    version: string;            // 如 "2.6.0"
    siteStartDate: string;      // 固定基準起點
    activityLevels: ActivityLevelConfig[];
    contentDensityLevels: ContentDensityLevelConfig[];
  };
  activity: Array<{
    date: string;               // "YYYY-MM-DD"
    count: number;              // 當日聚合事件數
    level: 0 | 1 | 2 | 3 | 4;   // 5 級量化色階
  }>;
}
```

### 11.1 欄位不變性與邊緣計算約束

1. **型別檢查**：消費端應確認數值欄位是可用的非負整數或浮點數；發生錯誤時，先依 `ok` 與 HTTP 狀態判斷，不能把缺失欄位靜默當成零；
2. **時間戳限制**：`servedAt` 是函式處理請求的時間，`generatedAt` 是快照生成時間。目前程式碼沒有宣告或強制兩者的單調關係，不能僅憑欄位名稱推定部署或系統時鐘一定正確；
3. **負載體積檢查**：`activity` 目前由程式產生 364 個日曆格，但 JSON 的實際大小會受文章標題、連結與部署資產影響。32 KB、6 KB 或固定執行時間都必須透過指定產物與環境重新測量，不能當成現行保證；
4. **相容性方向（PROPOSED）**：未來若新增欄位，應優先採取增量新增並保留既有核心欄位；這是演進原則，不代表所有歷史客戶端已獲得永久相容承諾。
