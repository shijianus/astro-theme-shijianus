# EpoCanvas 文件生命週期規範

<div class="article-aside">
  <p><span class="badge badge-primary">EES-006</span> <span class="badge badge-success">文件治理</span> <span class="badge badge-warning">以提交內容為準</span></p>
  <p>本規範定義官方文件如何建立、審閱、發布、修訂、標記差異與歸檔。它用來避免普通文章、歷史計畫、介面文案與服務端規則互相冒充權威。</p>
</div>

> [!IMPORTANT]
> 文件能被瀏覽不等於文件已經是目前規則。判斷一項說明是否有效，必須同時看其文件類型、狀態、更新日期、版本、對應程式碼/測試與是否已被正式提交。

## 1. 文件類型與權威層級

EpoCanvas 目前使用以下文件層級：

| 層級 | 位置 | 主要用途 | 權威邊界 |
| :--- | :--- | :--- | :--- |
| 社群政策 | `docs/community/` | 公開行為、隱私、帳號、內容權利、檢舉與安全通報 | 對外說明社群共同規則；不得單獨取代服務端鑑權 |
| 工程標準 | `docs/standards/` | 指標、內容、版本、系統與文件治理 | 對外說明目前工程口徑；需標示證據等級與已知差異 |
| 專案管理 | `docs/roadmap.md` | 已落地、已知差異與建議工作 | 表示優先順序與驗收方向，不是日期或功能保證 |
| 運維文件 | `docs/operations/` | 發布、回滾、事件與營運處理 | 描述操作流程與證據要求，不把未執行的步驟寫成已完成 |
| 普通文章 | `src/content/posts/` | 研究、教學、經驗、實驗與個人敘事 | 由文章作者負責；不自動成為政策、API 契約或服務承諾 |
| 根目錄說明 | `README*`、`GUIDES.md` 等 | 專案入門、開發與歷史背景 | 若與政策/標準或程式碼衝突，應修正連結與說法，不直接覆蓋專責文件 |

跨文件引用時，應優先連結專責文件而不是複製一份可能過期的規則。`USER_LEVEL_SPEC.md` 等尚未完成跨專案核驗的資料，應明確標示草案或內部參考，不得取代 `docs/community/` 的公開政策。

## 2. 狀態機與可引用程度

文件與文件中的工作項目可以使用以下狀態：

| 狀態 | 意義 | 可否作為目前規則引用 |
| :--- | :--- | :--- |
| `DRAFT` | 尚在撰寫或等待範圍確認 | 不可；只能作為討論材料 |
| `ACTIVE` | 已審閱、已提交，且目前適用 | 可以，但仍須看證據等級與更新日期 |
| `KNOWN-GAP` | 已確認與另一條鏈路或版本存在差異 | 可以引用差異本身，不可宣稱已統一 |
| `PROPOSED` | 尚未落地的設計、測試或運維能力 | 不可當作現有功能承諾 |
| `DEPRECATED` | 保留供遷移或歷史查閱，不再建議新使用 | 只能說明歷史背景，不可作為新實作依據 |
| `ARCHIVED` | 已完成保存或停止維護 | 只可在明確標示歷史語境時引用 |
| `BLOCKED` | 因憑證、平台、權利或外部決策而無法繼續 | 應同時說明阻塞條件與替代方案 |

頁面 front matter 的 `draft: true` 代表不應作為已發布文件使用。若正文只描述部分已驗證行為，應使用表格或段落把 `SOURCE-VERIFIED`、`TEST-VERIFIED`、`LIVE-VERIFIED`、`KNOWN-GAP` 與 `PROPOSED` 分開，不要只在標題上寫「官方」便省略證據。

## 3. 建立與審閱流程

一份新的官方文件至少經過以下步驟：

1. **定義範圍**：寫清楚讀者、適用功能、不包含項目與文件類型；
2. **收集證據**：核對程式碼、設定、資料表、測試、部署記錄或公開服務行為；
3. **起草正文**：使用正體中文作為目前官方政策/標準基線，將未完成內容標為 `PROPOSED` 或 `KNOWN-GAP`；
4. **交叉審閱**：檢查政策、程式碼、測試、連結、權限與個資邊界是否一致；
5. **正式提交**：使用可描述的 Git Commit 保存文件與必要的程式碼/測試變更；
6. **發布核驗**：若涉及線上頁面，記錄目標路由、建置/部署識別與驗證時間；
7. **持續維護**：功能、資料流、第三方服務或法律要求變更時，重新檢查相應段落。

只有完成範圍與審閱的文件，才能從 `DRAFT` 進入 `ACTIVE`。本地檔案存在、靜態頁面可生成或單次瀏覽器點擊，都不足以單獨證明生產功能已啟用。

## 4. 版本、日期與變更分類

官方標準使用 `MAJOR.MINOR.PATCH` 的語意化思路，詳細版本追溯見[版本與架構規範](/version/)。

- `MAJOR`：改變既有政策、資料語義、公開 API 或使用者可依賴的行為；
- `MINOR`：增加向後相容的章節、字段、流程或規則；
- `PATCH`：勘誤、來源補充、連結修正、術語統一與不改變契約的排版調整。

每次內容變更都應更新 `updatedDate`；若變更已改變讀者可依賴的規則，不得只自動增加 patch 而不在提交說明中交代影響。`pubDate` 表示文件首次作為該文件公開，不能因普通勘誤而回填成新的首次發布日。

## 5. 修訂、衝突與回溯

當文件與實作不一致時，維護者應先保護讀者與資料安全，再按下列順序處理：

1. 在文件中標示已知差異、受影響功能與暫時判定方式；
2. 以服務端權限、資料庫約束與實際錯誤回應作為安全邊界；
3. 修正文件、程式碼或測試中真正不一致的一側；
4. 補上可重跑的回歸測試或驗收紀錄；
5. 更新版本、日期、路由連結與路線圖狀態。

若無法確定哪一份文字最新，應查看 Git Commit、文件版本、部署識別與源碼，而不是依頁面排序、徽章顏色或文章發布時間猜測。錯誤文件可以先標記 `DEPRECATED` 或暫時隱藏，但不應在沒有替代說明時靜默刪除重要安全規則。

## 6. 棄用與歸檔

文件在以下情況可標記 `DEPRECATED` 或 `ARCHIVED`：

- 功能已移除，且新路由/流程已有替代文件；
- 規則已合併到另一份更專責的官方文件；
- 文件只描述歷史版本，不能再用於目前部署；
- 跨專案契約尚未核驗，暫時保留作為內部草案而非公開規則。

棄用文件應保留棄用原因、替代入口、適用的最後版本與日期。連結入口應導向目前有效的文件，避免新讀者從搜尋結果直接採用過期規則。

- [ ] API、權限、資料、支付與安全說法有源碼或測試依據。
