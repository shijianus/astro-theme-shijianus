# EpoCanvas 社群身份、等級與徽章說明

這篇文章是公開的社群功能說明，不是會員付費方案，也不是管理權限清單。它整理目前程式碼能確認的 `LV`、`TL`、角色與徽章行為，讓讀者知道哪些是可觀察的顯示、哪些是 API 的實際權限，以及哪些地方仍在統一中。

> [!IMPORTANT]
> 目前客戶端 `src/lib/user-level.ts` 與服務端 `functions/_lib/auth-service.ts` 各自存在一套等級計算。本文不把兩者包裝成已完全一致的單一契約；若帳號中心顯示與伺服器實際回應不同，以伺服器身份驗證與 API 權限為準。

> [!NOTE]
> 閱讀、留言、Reaction 與活躍資料可能受到瀏覽器 `LocalStorage`、登入會話、D1 可用性與統計同步時機影響。清除瀏覽器資料、切換裝置或使用無痕模式，可能使本機統計或徽章佩戴選擇消失；這不代表站方可以任意補發或保證永久保存某個數值。

## 1. 四個容易混淆的概念

| 名稱 | 目前用途 | 不是什麼 |
| :--- | :--- | :--- |
| `LV`（Level） | 帳號中心與作者名片可能顯示的社群階梯代號，範圍為 `LV.0` 至 `LV.4` | 不是文章付費牆、私有文章通行證或單獨的管理員權限 |
| `TL`（Trust Level） | 依活動統計、角色與部分特殊條件計算的信任值或顯示值 | 不是法律身份、付款等級或對所有 API 的通用授權 |
| 角色（Role） | 服務端使用 `visitor`、`reader`、`admin` 等角色執行鑑權 | 不是只靠前端 LocalStorage 就能自行修改的標籤 |
| 徽章（Badge） | 顯示閱讀、互動、活動或身份成就的圖示與文字 | 不是安全憑證，也不會取代有效會話與管理員驗證 |

讚賞與付款和社群晉升分離。完成讚賞不會自動增加 LV/TL，也不會解鎖付費文章、特殊評論配額或管理功能。

## 2. 客戶端目前使用的階梯

以下是 `computeUserLevel()` 可讀取的瀑布式階梯。後一階段必須先通過前一階段的條件；表中的 TL 是該稱號的客戶端上限，不是每個人一取得稱號就會立刻擁有的固定值。

| 階段 | 稱號 | 主要條件 | 客戶端 TL 上限 |
| :--- | :--- | :--- | ---: |
| `LV.0` | 新興使用者 | 尚未產生閱讀活動 | 0 |
| `LV.0` | 初始使用者 | 讀過文章，或閱讀時間至少 1 分鐘 | 2 |
| `LV.1` | 基本使用者 | 已完成初始階段，並至少發表 1 則留言 | 8 |
| `LV.1` | 貢獻者 | 閱讀至少 30 分鐘、留言至少 10 則 | 15 |
| `LV.1` | 思辨學者 | 前階段完成；閱讀至少 120 分鐘、留言至少 20 則、收到至少 10 次 Reaction | 20 |
| `LV.2` | 活躍使用者 | 前階段完成；活躍至少 20 天、閱讀至少 300 分鐘、留言至少 30 則、收到至少 20 次 Reaction | 35 |
| `LV.2` | 常青極客 | 前階段完成；活躍至少 45 天、閱讀至少 480 分鐘、留言至少 60 則、收到至少 40 次 Reaction | 50 |
| `LV.3` | 先驅 | 前階段完成；活躍至少 90 天、閱讀至少 720 分鐘、留言至少 100 則、收到至少 60 次 Reaction | 70 |
| `LV.3` | 年度使用者 | 先完成先驅，再達到活躍 180 天、閱讀 1440 分鐘、留言 150 則 | 80 |
| `LV.3` | 墨海宗師 | 先完成年度使用者，再達到活躍 300 天、閱讀 2160 分鐘、收到至少 100 次 Reaction | 90 |
| `LV.4` | 核心成員 | 由管理角色或站務設定授予，不是一般自動晉升 | 91–99 |
| `LV.4` | 站長 | 由站長/管理員身份判定 | 100（客戶端引擎） |

這些統計只用來描述社群參與歷程。它們不會把一般讀者變成管理員，也不會改變評論 API 對登入、限流、公開資料與 Reaction 的安全檢查。

## 3. 服務端身份為什麼可能不同

服務端 `calculateUserLevel()` 目前使用帳號建立天數、資料庫中的留言數、收到的 Like，以及由這些資料推導的閱讀分鐘與文章數；它還會把結果映射到 `user_lv0`、`user_lv1` 或 `user_base`。服務端同時會檢查：

- 有效的登入會話與帳號角色；
- Epomail 身份來源與管理員授權；
- 站長的設定信箱或管理員環境變數；
- 服務端資料庫可取得的統計，而不是任意相信前端傳來的 LV/TL。

因此，以下情況都可能在過渡期出現：

1. 本機帳號中心的稱號與服務端回傳稱號不同；
2. 評論作者卡片與帳號中心使用不同統計時間點；
3. 客戶端顯示 `TL.100` 的站長，而服務端帳號等級映射顯示 `TL.99` 的站長資料；
4. 登出、會話過期或切換裝置後，本機的活動統計仍在，但 API 權限已回到訪客或未驗證狀態。

這些是工程上待統一的資料契約，不是讀者需要自行猜測或以重複留言修正的問題。若差異影響實際權限，請以服務端回應為準並提交回報。

## 4. 徽章引擎目前判定的類別

客戶端 `evaluateUserBadges()` 會依傳入的統計與身份上下文產生已解鎖徽章，並按 `priority` 由高至低排序。部分目前可觀察的條件如下：

| 類別 | 代表徽章 | 判定資料 |
| :--- | :--- | :--- |
| 等級主稱號 | 新興使用者、貢獻者、常青極客、先驅、墨海宗師、站長等 | `computeUserLevel()` 的階梯、角色、信箱與活動統計 |
| 閱讀沉澱 | 通讀全文、慢讀時光、博覽群書、學貫中西、墨海領航 | 閱讀分鐘數達到 15、120、600、1800、3600 等門檻 |
| 互動交流 | 初露鋒芒、豐富表情、言之有物、真知灼見、縱論古今、回音激盪 | 編輯過留言、使用 Emoji、留言數或提及/引用上下文 |
| Reaction | 初見迴響、引發共鳴、深得人心、眾望所歸、不吝讚美、樂善好施 | 收到或送出的 Reaction 數量 |
| 活動與資料 | 信件連結、自傳作者、常客印記、見縫插針、百日墨客、同舟一載、堅韌長青 | 信箱、簡介/頭像、活躍天數與註冊天數 |
| 特殊標籤 | 創世墨客、架構見證人、種子使用者、鐵桿粉絲、破曉布道者、領跑者 | 客戶端上下文中的活動、留言、Reaction、編輯等條件 |

「特殊」或「絕版」是目前徽章名稱與描述中的分類文字，不應被解讀為已提供不可撤銷的歷史授予、TL 額外加成或管理權。這些徽章是顯示層成就，真正的角色與權限仍由服務端驗證。

## 5. 徽章佩戴與展示的實際規則

客戶端提供最多 4 枚佩戴項目的本機設定：

1. `writeEquippedBadges()` 會去除重複 ID，並截取前 4 枚；
2. `getEquippedBadges()` 只會從目前已解鎖徽章中解析所選 ID；
3. 如果沒有手動選擇佩戴項目，`getEquippedBadges()` 會回傳空陣列；
4. 清除瀏覽器的 `LocalStorage` 可能使本機佩戴選擇消失；
5. 顯示 4 枚徽章不代表其他徽章被撤銷，也不代表其中任何一枚取得 API 權限。

因此，現行規則不是「沒有設定時自動顯示最高權重前四枚」。`computeOfficialBadges()` 雖然可以提供排序後的前四項作為相容資料，但名片佩戴流程仍以使用者實際選擇為準。

## 6. 身份群組與頭像樣式

`getAuthorGroups()` 目前會依管理員身份、Epomail 提供者或一般讀者回傳有限的官方群組文字，包括站長團隊、核心架構師、Epomail 認證讀者、郵件公測組與社群讀者圈。這些是公開群組標籤，不是可由使用者自由輸入的權限字段。

客戶端引擎對站長設定 `isSquareAvatar: true`，對一般讀者通常使用圓形頭像；實際顯示仍受元件、身份來源與 CSS 影響。不要以頭像形狀單獨判定管理員，應以帳號角色與服務端鑑權為準。

## 7. 公平使用與資料修正

刷留言、重複內容、刷 Reaction、偽造閱讀活動、冒用站長或用付款交換頭銜，都違反社群公約。站方可以在發現錯誤或濫用時修正統計、隱藏徽章、撤銷錯誤標籤或限制帳號，不保證由錯誤資料產生的顯示永久保留。

若你的身份、徽章、地區顯示或作者卡片明顯錯誤，請提供文章網址、時間、目前顯示與實際登入狀態，透過[檢舉與申訴說明](/community/reporting-and-appeals/)聯絡站方。請不要公開貼出電子郵件、會話令牌、原始 IP 或管理欄位。
